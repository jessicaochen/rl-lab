# Experiment: py-inference-scheduler request routing vs verl's balancer

**Question.** When the sampler is several vLLM replicas, how much does routing
each policy request with [py-inference-scheduler](https://github.com/llm-d-incubation/py-inference-scheduler)
(load-, KV- and prefix-aware scoring per request) change generation — per-turn
latency and its tail, time-to-first-token and queue time at the engines,
prefix-cache reuse, balance across replicas — and does that reach step time?

**Rung.** `h200-t16-s4x2` (`benchmark/setups/verl-qwen-30b-swe/config/h200-t16-s4x2`):
Qwen3-30B-A3B-Thinking-2507, trainer 2×8 H200 (Megatron TP2·CP1·EP4, DP2),
sampler 8 H200 as **4 vLLM replicas × TP2**, batch 64 prompts × 8 rollouts,
128 concurrent agent sessions, 2 steps, validation off. Hybrid replicas on the
trainer GPUs (8 × TP2) take part in rollouts until step 1's training, in both arms.

## Arms

| run | `--feature` | profile | who picks the replica per request |
|---|---|---|---|
| baseline | — | — | verl `GlobalRequestLoadBalancer`: sticky per session (uni-agent session id = verl request id), least-inflight when a session starts |
| prefix-only | `inference-scheduler` | `scheduler-prefix.yaml`: `prefix_cache` 1.0, `max_score` | the treatment of upstream's own SWE-bench A/B ("soft stickiness"): the replica holding the longest cached prefix of the prompt; a prompt with no cached prefix anywhere goes to the least-loaded replica *as seen by this gateway* |
| backpressure | `inference-scheduler` | `scheduler-backpressure.yaml`: `waiting_queue` 5, `least_queue` 2, `kv_cache` 1, `prefix_cache` 1 | the repo's verl example profile |

All arms: image v9, one scheduler per gateway actor (8), verl's balancer as fallback,
identical always-on instrumentation (`rlbench_verl_provider.rollout_adapter`): one
record per policy request at the gateway, a `/metrics` snapshot per replica every 30 s.
See `benchmark/setups/verl-qwen-30b-swe/features/inference-scheduler/README.md`.

## Commands

```
# rlbench commands run from benchmark/, the comparison from the repo root
V=setups/verl-qwen-30b-swe
COMMON="--config $V/config/h200-t16-s4x2 --keep --var VAL_TASKS=0 --timeout 3h"
rlbench run $V $COMMON --name h200-t16-s4x2
rlbench run $V $COMMON --name h200-t16-s4x2-sched-prefix --feature inference-scheduler
rlbench run $V $COMMON --name h200-t16-s4x2-sched --feature inference-scheduler --var SCHEDULER_CONFIG=scheduler-backpressure.yaml
python3 benchmark/setups/verl-qwen-30b-swe/tools/compare_runs.py baseline=benchmark/runs/<id> prefix-only=benchmark/runs/<id> backpressure=benchmark/runs/<id>
python3 benchmark/setups/verl-qwen-30b-swe/features/inference-scheduler/report.py benchmark/runs/<id>
```

### Reading the table

- **Generation was impacted in both treatment arms — negatively — for two different
  reasons.** By upstream's own metric, mean generation time per trajectory went from
  106 s (baseline) to 112 s with the prefix-only profile (+6 %) and 108 s with the
  backpressure profile (+2 %, noise); the slowest trajectory went from 321 s to 397 s
  and 400 s (+24 %). Per-turn p99 moved from 78 s to 93 s (prefix-only) and 82 s
  (backpressure). Step 2 took 642 s and 627 s against 581 s (+10 %, +8 %; the second
  baseline at 632 s shows most of the step-time delta is noise, the per-turn tails and
  the per-replica numbers are not).
- **Prefix-only (upstream's treatment) restores stickiness and then unbalances the
  replicas.** Stickiness is perfect (0 trajectories on more than one replica, prefix-hit
  rate 0.934 = baseline 0.936, prefill 48 ms vs 53 ms), i.e. the scheduler delivers
  exactly what the profile asks for. But the 8 GRPO rollouts of one task share their
  initial prompt verbatim, so they all follow the first sibling to one replica; and the
  only load signal in this profile is the no-match fallback, which sees one gateway's
  inflight count (8 gateways, each ~16 sessions). The outcome is placement at task
  granularity with a 1/8 view of load: two replicas carried twice the requests and
  tokens of the other two (request share CV 0.335 vs 0.013). Decode is the cost here:
  the busy replicas ran ~2× the concurrent sequences, their mean engine latency was
  18.2 s vs 11.4 s on the light ones, TTFT 0.37 s vs 0.26 s, and the batch's tail is set
  by the busy pair.
- **Backpressure (the repo's example) keeps balance but breaks stickiness.** With no
  engine ever queuing (`waiting` 0), `least_queue` outvoted `prefix_cache` and 38 % of
  trajectories changed replica mid-session; prefix hits fell to 0.885 and each move
  paid a fresh prefill. The absolute cost is small on this workload (prefill 58 ms
  against 14 s per turn) and the step-time delta is inside the noise band.
- **Why upstream's −10 % does not transfer.** Their A/B ran a 7B model with 47 turns of
  ~190 generated tokens on a 4k prompt: prefill is a double-digit share of generation
  there, so routing a turn to the replica that holds its prefix is worth real time.
  Here a turn is ~1.2k generated tokens on an 8k prompt: prefill is 0.4 % of the
  turn (53 ms of 14 s), and the baseline is already session-sticky with a 94 %
  prefix-hit rate, so there is nothing left for prefix affinity to win and every
  placement mistake costs decode time instead. The engines are also far from
  saturated (18 running sequences, 9 % KV, no queue), so the load-aware scorers never
  had a signal either.
- **Bottom line:** the feature is correctly wired (both profiles active on every
  request, zero fallbacks, membership tracking verl's balancer) and the evidence
  resolves its effect: on this rung verl's session-sticky least-inflight baseline is
  the better router. A profile that could compete here needs both terms at once — the
  prefix scorer for stickiness *and* a global load term that counts sessions (not this
  gateway's inflight) with a weight that only breaks stickiness when load is actually
  unequal — and the honest test of a load-aware router is a saturated sampler
  (same 128 sessions on 2 × TP2, i.e. a `h200-t16-s2x2` rung, or `kv_saturation` flow
  control once engines queue). Neither was run; they are the next experiment if wanted.

### Caveats

- The baseline's rlbench watcher died 12 minutes in (host lost DNS); the in-cluster
  job completed and the run folder was recovered with `rlbench collect` +
  `hooks/post-run.sh`, so its DCGM samples cover only the first 12 minutes and
  `result.json` timings are not meaningful (tools use the k8s job window). Gateway
  records, replica `/metrics` snapshots and agent logs are complete.
- Scheduler state is per gateway actor (8 of them): `least_queue`, the no-match
  fallback and the prefix index see one gateway's share of the traffic; the
  engine-reported inputs are global. Upstream's hook has the same shape (one
  scheduler per AgentLoopWorker).
- Histogram quantiles from `/metrics` are bucket upper bounds; means are exact.
- Two steps per arm, one comparable step; generation also depends on what the agent
  does at temperature 1.0 (response length 11.7k–12.7k tokens in step 2), so the
  table carries response length and turns. Effects below ~8 % on step time are not
  resolvable with this design; the per-replica imbalance is not a noise effect.

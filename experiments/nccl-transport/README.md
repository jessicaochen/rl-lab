# Experiment: NCCL intra-node transport vs RL step time

**Question.** How much do RL training and sampling slow down when NCCL's fast
intra-node paths are taken away? Intra-GPU communication on an H200 node
normally runs over NVLink: NVLS (NVLink SHARP, in-switch reductions) for
collectives and NVLink peer-to-peer copies for everything else. We remove
those one at a time and measure the same 2-step benchmark.

**Rung.** `h200-t8-s2` from the scalability ladder
(`benchmark/setups/verl-qwen-30b-swe/config/h200-t8-s2`): Qwen3-30B-A3B-Thinking-2507,
trainer 1×8 H200 (Megatron TP2·CP1·EP4, DP1 — every trainer collective is
intra-node), sampler 2 H200 (vLLM TP2, intra-node), batch 32 prompts × 8
rollouts, 48 concurrent agent sessions, 2 steps, validation off.

## Variants

| run | NCCL env | what changes inside the node |
|---|---|---|
| baseline | defaults | NVLS collectives + NVLink P2P |
| nvls-off | `NCCL_NVLS_ENABLE=0` | collectives fall back to ring/tree over NVLink P2P |
| nvls-p2p-off | `NCCL_NVLS_ENABLE=0 NCCL_P2P_DISABLE=1` | no peer copies: ranks exchange through host shared memory (PCIe) |

Who is affected: Megatron TP all-reduce / reduce-scatter / all-gather and EP
all-to-all (training), vLLM TP2 collectives (sampling — note vLLM's custom
all-reduce uses CUDA IPC directly and is *not* governed by NCCL env vars, so
the sampler side may move less than the trainer), and the NCCL checkpoint
engine that broadcasts weights trainer → sampler (sync; this leg crosses nodes
over TCP in every variant, so it should barely move).

How the variables are applied: `--var 'RAY_ENV_VARS=...'` → `common.sh` turns
each `K=V` into a verl hydra override
`+ray_kwargs.ray_init.runtime_env.env_vars.K=V`, which verl merges into the Ray
job runtime env, so every Ray actor (trainer ranks, vLLM servers and their
engine processes, weight-sync engine) sees them. `NCCL_DEBUG=INFO
NCCL_DEBUG_SUBSYS=INIT,ENV` is added to the new runs so the driver log itself
proves which transport NCCL selected (`set by environment to`, `via P2P/CUMEM`
vs `via SHM` channel lines). No RayCluster/pod change between runs.

### Reading the table

- **Turning NVLS off costs nothing measurable at this scale.** Every timing
  of `nvls-off` is within ±5 % of the baseline (step 2: 998 s vs 1038 s;
  `update_actor` 312 s vs 324 s; MFU 6.4 % vs 6.7 %). With TP2 and EP4 inside
  one node, the collectives are 2- and 4-rank operations that gain little
  from in-switch reduction; the ring/tree fallback over NVLink P2P is as fast.
  (The log confirms the ranks still connected `via P2P/IPC` and `via P2P/CUMEM`.)
- **Turning NVLink P2P off is the cliff — for training.** With every
  intra-node channel `via SHM/direct` (host memory over PCIe), the trainer's
  `old_log_prob` took 4.1× longer and `update_actor` 5.0× longer; actor MFU
  fell from 6.7 % to 0.97 % (66 → 10 TFLOP/s per GPU). Step time went from
  1038 s to 2184 s (2.1×) only because generation of the next batch was
  completely hidden behind the slow update (`timing_s/gen` = 0.12 s). The
  weight sync (trainer → sampler, TCP across nodes in every variant) stayed at
  ~13-15 s.
- **Sampling was essentially unaffected per session.** Policy tokens per
  second per running agent session were 60.2 (baseline), 61.5, and 59.3 —
  flat. The 2-GPU vLLM sampler at TP2 does its all-reduce through its own
  CUDA-IPC custom kernel, not NCCL, and the agent loop (tool calls, sandbox
  I/O) dominates per-session latency anyway. The lower *window-based*
  sampler throughput in `nvls-p2p-off` (1033 vs 1356 tok/s/GPU) is a
  tail-effect, not a speed effect: the sampler ran ahead of the slow trainer
  and produced a third batch (768 sessions vs 556/563) whose tail was still
  draining when the 2-step job ended, so the active window includes more
  ramp-down time per useful batch. That run-ahead also shows as off-policy
  staleness 1.0 (vs 0.2): step 2 trained on data one update older.
- **Bottom line for this topology:** NVLS is optional; NVLink P2P is not. A
  node without P2P turns a 60 %-busy trainer into the bottleneck by 4-5× and
  halves end-to-end throughput even though the sampler keeps up.

## Caveats

- Step 1 includes first-batch effects; **step 2 is the comparable data
  point** (ladder convention). Generation time also depends on what the agent
  does (turns, response length), which varies run to run at temperature 1.0 —
  the table carries response length and turns so that variance is visible.
- The sampler's TP2 all-reduce in vLLM bypasses NCCL (custom all-reduce over
  CUDA IPC), so `NCCL_P2P_DISABLE` may under-state the sampling impact a
  P2P-less fabric would have.
- **verl's `timing_s/gen` is the trainer's wait for a batch, not sampler
  speed.** In `separate_async` it reads ~0 whenever generation overlapped the
  previous update (as in `nvls-p2p-off` step 2). Sampler-side rows are
  therefore derived from uni-agent's per-session `framework.log` in
  `agent-logs.tar.gz` (start/scored timestamps, `model_tokens`), which all
  three run folders have.
- The baseline's 556 sessions include an 8-session retry of one task group
  that failed under tool image v1 (`num_failed_uids=1`), which extends its
  sampler window by ~3 min.
